# 原始配置重解码与引用内容修复

2026-10-31 收到的 `roco_extract.zip` 使此前的字段错绑推断能够用原始字节复算。本次完成 `MESSAGE_CONF`、`TASK_CONF`、`REWARD_CONF`、`SELECT_CONF` 四张表的重解码；固定的 `data/current.zip` 仍保留原始字节。

**引用内容现在可导出 659 条有来源的记录：255 条由原始二进制验证，404 条延续已有历史补缺。原清单中的 171 条字段冲突和奖励 19589 的无定义状态，在这个新导出中均已处理。** 这项计数只覆盖已登记引用集合，不代表整个游戏的数据或运行时语义已经核准。

## 直接使用

在仓库根目录使用 Python 3.10+，不需要另装依赖，也不需要重新下载客户端：

```powershell
# 逐个校验原始文件，重解全部配对，并比对已提交证据
python tools/raw_content.py verify

# 导出引用集合、四张修复后的整表，以及较新补丁的独立视图
python tools/raw_content.py export --output-dir build/raw-content

# 查询本轮已恢复的奖励原始定义及字节来源
python tools/raw_content.py get --table REWARD_CONF --id 19589
```

`get` 面向登记的引用集合；其余 ID 请读取导出的整表。输出目录必须位于原始数据目录之外，命令会拒绝覆盖 `data/`、历史 Pak 目录或源输入。

| 输出 | 内容与使用边界 |
| --- | --- |
| `referenced_content_resolved.json` | 本轮 659 条引用资料；每条保留二进制或历史来源状态。接续 M2-00 时使用此文件。 |
| `binary_content_recovery.json` | 255 条原始字节修复／补充记录，含旧记录指纹、变化的 JSON Pointer、原始行位置与本地化索引。 |
| `snapshot_repair/*.json` | 与固定快照各表 ID 集合一致的四张完整重解表；修正同一份数据的 Schema／文字绑定。 |
| `latest_supplied/*.json` | 本次交付中各表最大补丁编号的数据，配对来源明确列出；没有把它声明为实际游戏运行时生效表。 |
| `raw_content_audit.json` | 52 个数据配对的哈希、记录数、边界校验和当前错误输出的完整复现证据。 |

整表沿用 `RocoDataRows` 结构，增加 `source_pairing`、`view` 和 `runtime_mount_order_verified`。文字已经按配对资源解析，`LocalizationStrings` 为空；完整原始本地化资源与索引证明仍在来源包和审计记录中。

旧 `tools/content_supplement.py` 保留历史恢复路径及原来的 487／171／1 统计，便于复算旧结论。它不会自动变更为本次二进制修复路径；需要新结果时运行上面的 `raw_content.py`。

## 四表错误如何复现

按下列组合读取原始字节，可以与固定 `current.zip` 的对应 `RocoDataRows` **逐 ID、逐字段完全一致**：

| 表 | 原数据层 | 复现所用 Schema | 复现所用文本池 | 完全一致行数 |
| --- | --- | --- | --- | ---: |
| MESSAGE | base | 3_P（本地化类型） | 1_P `dev_CN` | 58 |
| TASK | 3_P | 3_P | 1_P `dev_CN` | 5,542 |
| REWARD | 0_P | 3_P | 1_P `dev_CN` | 7,826 |
| SELECT | 2_P | 2_P | 1_P `dev_CN` | 11,520 |

MESSAGE 使用 0_P 文本池也能完全复现相同 58 行，因此不能据此唯一确定当时选择了 0_P 还是 1_P。以上是明确输入组合的反事实复现，没有声称读取了原导出程序日志。

当前 ZIP 附带的四份 `BinLocalize/zh_Hans/*.json` 却都精确等于本次原始 **0_P** 本地化资源。任务、奖励、选项的实际文本结果需要 **1_P** 池才能完整复现，证明这些导出文件不能被当作一套相互一致的解码输入。

错误配对还使 TASK 的 4,035 个本地化字段引用和 SELECT 的 1,829 个引用查不到索引而输出空字符串。正确配对后的所有 52 个数据版本均无缺失的本地化索引。

### MESSAGE

本次收到的 **3_P 原始 `.non` 与 0_P 字节完全相同**，`myname`、`sender`、`text`、`receive_des` 均为 `ELocalizedString`。此前粘贴文本把 3_P 描述成与 base 一样的 `EString`；该声明已被原文件证据更正。

base 数据使用内嵌字符串常量。将其数值索引错误地用于外部本地化池，就会得到当前字段错位。四封信的发送人恢复为：

| ID | 内嵌常量索引 | 正确发送人 |
| --- | ---: | --- |
| 10023 | 46 | 斯凯勒 |
| 10034 | 72 | 教导主任 噜噜 |
| 10035 | 75 | 格里芬院长 |
| 55000 | 151 | 露萌 |

缺失的 56000、56002、56003 从本次 3_P 原数据读取，标为另一个 Pak 来源的缺失记录补充。

### TASK 与 SELECT

TASK 的 3_P 原数据对应 43 字段 Schema；SELECT 的 2_P 原数据对应重排后的 26 字段 Schema。修复它们的本地化绑定后，**5,542 条任务和 11,520 条选项的所有非字符串字段均与固定快照一致**。因此没有因为修正文案而用旧任务结构整体替换现有条件、动作或奖励引用。

原清单中的三个任务正文冲突和 130 个选项文本冲突，现在均有相应原始索引与正确文本池的直接依据。

### REWARD

0_P 原数据仍有第 9 字段 `ObtainLimit`，真实 `RewardItem` 在第 12 字段；3_P Schema 把第 9 字段定义成 `RewardItem`。用该错误组合读取时，原限额数值被当成数组常量索引，精确复现当前全部 623 份载荷，包括 611 份 `[{"Type":22,"Count":1000000}]`。错误配对有 7,735 行留下未消费行尾，逐行重新定位让这种问题未必自然触发旧解析器异常。

正确的 0_P Schema 能恢复实际奖励数组、数量及旧版权重字段。原清单的 66 个缺少数组和 34 个错误数组由此得到原始字节证明；既有 14 个缺失奖励与新找到的 19589 从 3_P 原数据补充。

本次 **10_P 的 Schema 与数据均已收到**。10_P 与 3_P Schema 的唯一语义差异为 `RewardItem.ArrayDim: 25 → 34`。实际元素数仍来自数组常量载荷长度；工具不会把数组补齐为 25 或 34 个元素。

## 奖励 19589

17 份 REWARD 原数据中，base／0_P／1_P／2_P 不含 19589；其余 **13 层**均含以下数值定义，且奖励组件字节一致：

```json
{
  "id": 19589,
  "Name": "S3赛季手册-周常任务奖励",
  "Type": 1,
  "DisplayName": "S3赛季手册-周常章节任务奖励",
  "Description": "40赛季token",
  "RewardItem": [{"Type": 2, "Id": 77, "Count": 40}]
}
```

引用补充包选择 3_P 作为最早已提供定义的来源，较新视图使用 35_P。记录的行索引为 594、偏移 15162、长度 26，奖励组件原字节为 `e0020000004d00000028000000`。审计文件保留每个版本的原始行位置、哈希及文字索引。

历史 2_P `VISUAL_ITEM_CONF/77` 的显示名为“幻梦代币”；它是历史身份候选。本次没有提供该身份表的原文件，固定快照也缺少 77，故这次证明的是奖励三元组和同源说明文字，尚未证明当前客户端的类型分派、身份表或实际结算行为。

## 验证规则与边界

全部 52 个配对共重解 **345,270 行**，所有本地化引用均能解析，没有未消费记录尾部、非法常量索引或越界读取。原始文件、解码记录内容及引用补充均可从已提交来源包再次生成。

两份 base 文件带固定的额外存在位：MESSAGE 每行 bit 11，SELECT 每行 bits 29、30。这些位在该 Schema 最后一个存在位字节的未使用区，所有声明字段仍恰好消费整行。manifest 只对这两份已固定哈希的文件显式允许相应位置，并在审计中统计；其他位置、其他文件和任何嵌套结构不继承此例外。

读取器依据固定版本的 [CUE4Parse `FRocoBinData.cs`](https://github.com/FabianFG/CUE4Parse/blob/2a159ad0702120db30fdd85c1219dff78e5204b8/CUE4Parse/GameTypes/Tencent/RocoKingdomWorld/Assets/Objects/FRocoBinData.cs) 的结构，另加严格边界、记录完整消费、索引覆盖与重复 ID 检查。`ELocalizedString` 按键存在性查找，保留索引空洞；`EString` 使用本文件常量表。字段缺失不会自动填成零、空数组或 `null`。未压缩的 `BinData` 格式不在该工具支持范围内。

仍需单独核验的项目是条件／动作枚举的执行语义、奖励类型到当前身份表的完整对应、游戏运行时生效顺序及剩余地图身份关联。本次四表交付没有包含这些实现或资源，不能因引用记录统计归零而宣称整个 M2-00 资料阶段完成。
